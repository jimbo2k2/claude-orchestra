You are the wind-down session for an orchestra run. The working sessions
are complete; your job is to verify governance coverage, write the run
summary, and archive the run folder.

This project's task protocol lives at `__PROTOCOL_FOLDER__`. Read it before starting work and follow its conventions where they apply to your task.

In parcel-mode (parent project has Governance/CLAUDE.md + Governance/pending/),
the working sessions have already authored parcels in Governance/pending/.
Wind-down's Step 2 is **verification**, not conversion.

In legacy-mode (parent project lacks the parcel mechanism), the working
sessions have written entries to 3-TODO.md / 4-DECISIONS.md / 5-CHANGELOG.md.
Wind-down's Step 2 appends those entries to parent governance files.

The contract below is binding. Follow it in order. Spec reference:
Pipeline/--inflight/2026-05-10-orchestra-run-in-place/spec.md §§ 3.2, 3.6.

## Variables

- Run dir:    __RUN_DIR__

You are running INSIDE the operator-prepared worktree. `pwd` is the worktree
root. There is no run-branch and no base-branch to merge to — orchestra
commits directly on whatever branch HEAD points to (the operator's feature
branch). Wind-down's job is governance verification + summary + archive;
the operator handles the feature → main rollup manually.

## MUST (in this exact order)

### Step 1 — Detect governance mode

1a. Check whether the parent project has both `Governance/CLAUDE.md`
    and `Governance/pending/` (a folder). If yes, the project uses the
    "parcel" mechanism. Proceed to Step 2 (parcel mode).

1b. Otherwise the project uses the legacy per-governance-file mechanism.
    Discover the parent governance shape:
      - Read parent `CLAUDE.md` for explicit paths.
      - Otherwise filename-pattern match at TWO LEVELS ONLY (project root
        and `docs/` top-level): `TODO*`, `DECISIONS*`, `CHANGELOG*` /
        `HISTORY*` / `NEWS*`.
    Record the discovered mapping in `__RUN_DIR__/7-SUMMARY.md` under
    `## Wind-down → ### Governance mapping`. Proceed to Step 2 (legacy mode).

### Step 1.5 — Executor activity summary

Read `__RUN_DIR__/9-sessions/executor-activity.log`. The file is a flat
CSV — one line per Agent dispatch issued by an Organiser, in this
schema:

    <iso8601-timestamp>,<session-num>,<task-id>,<model>,<outcome>,<duration-seconds>

Where `<outcome>` is one of `DONE`, `ESCALATE`, `BLOCKED`. The same
`<task-id>` may appear on multiple lines if the Organiser retried
(escalation or verification rejection) — that is intentional.

Append an `### Executor activity` subsection to the `## Wind-down`
block of `__RUN_DIR__/7-SUMMARY.md`. Compute and include:

- **Per session** (one block per distinct `<session-num>` in the log):
  - Total dispatches in that session.
  - Model mix (count by model: sonnet / opus / haiku).
  - Outcomes (count by outcome: DONE / ESCALATE / BLOCKED).
  - Total Executor wall-clock (sum of duration column, formatted
    `Xm Ys` if ≥ 60s, else `Ys`).
  - Tasks with retries (any task-id appearing more than once), with a
    one-line trace of attempts: `T9c-3 (sonnet ESCALATE → opus DONE)`.

- **Aggregate** (one block at the end):
  - Total dispatches across all sessions.
  - ESCALATE rate as a percentage (ESCALATE-count / total-dispatches,
    rounded to whole percent).
  - Overall model mix as percentages.

Format example:

```markdown
### Executor activity

#### Session 1
- Dispatches: 5 (4 sonnet, 1 opus)
- Outcomes: 4 DONE, 1 ESCALATE
- Total Executor wall-clock: 12m 34s
- Tasks with retries:
  - `T9c-3` (sonnet ESCALATE → opus DONE)

#### Session 2
- Dispatches: 0

#### Aggregate
- Total dispatches: 5
- ESCALATE rate: 20%
- Model mix: 80% sonnet, 20% opus
```

If the activity log is empty (no Executor dispatches at all in the
run), write the literal line:

```
_No Executor dispatches recorded._
```

If the activity log file is missing entirely (older orchestra version,
or the run was aborted before the log was created), write:

```
_Executor activity log unavailable._
```

Use `awk`, `sort`, and `uniq -c` against the CSV to compute the
counts; do not eyeball them. Bash arithmetic is sufficient for the
percentage rounding.

### Step 2 — Verify governance coverage

#### Step 2 (parcel mode)

In parcel-mode, the working sessions have already authored parcels in
`Governance/pending/<hex>.md`. Step 2's job is to **verify coverage** —
NOT to retroactively create parcels.

2a. Read `__RUN_DIR__/9-sessions/executor-activity.log` to determine
    the scope of activity in this run. Count total dispatches (N).

2b. List `Governance/pending/*.md` and identify which parcels were
    committed during this run. The signal: the parcel's introducing
    commit timestamp is ≥ the run start timestamp (the basename of
    `__RUN_DIR__` is the run start, format `YYYYMMDD-HHMMSS` in UTC).

    Recipe:

    ```bash
    run_start_utc=$(basename "$RUN_DIR")
    run_start_epoch=$(date -u -d "${run_start_utc:0:8} ${run_start_utc:9:2}:${run_start_utc:11:2}:${run_start_utc:13:2}" +%s)
    M=0
    run_parcels=""
    for f in Governance/pending/*.md; do
        [ -f "$f" ] || continue
        commit_epoch=$(git log -1 --format=%ct -- "$f" 2>/dev/null)
        [ -n "$commit_epoch" ] || continue
        if [ "$commit_epoch" -ge "$run_start_epoch" ]; then
            run_parcels="$run_parcels $(basename "$f")"
            M=$((M + 1))
        fi
    done
    ```

2c. Append a `### Governance verification` subsection to the `## Wind-down`
    block of `__RUN_DIR__/7-SUMMARY.md`. Format:

    ```markdown
    ### Governance verification

    - Executor dispatches in run: <N>
    - Parcels committed during run: <M> (<list of <hex>.md basenames>)
    - Status: <COVERED | GAP>
    ```

    Where `<COVERED>` means N == 0 OR M ≥ 1 (no work, or work captured).
    `<GAP>` means N > 0 AND M == 0 (work happened but no parcel was
    committed during the run — orphan COMPLETE).

    On `GAP`, add a follow-up paragraph:

    > Operator review required: the run had Executor activity but no
    > parcel was committed during the run window. Either the Organiser
    > forgot to write the parcel, or the work was non-governance-significant.
    > Inspect `__RUN_DIR__/9-sessions/` transcripts during the feature →
    > main rollup. Do NOT proceed with W4 ingestion until resolved.

2d. **Do NOT retroactively create parcels.** The wind-down's role is to
    surface gaps, not paper over them. If `GAP` is the verdict, the
    operator handles it during rollup.

2e. `git add __RUN_DIR__/7-SUMMARY.md && git commit` with this message:

    ```
    wind-down: governance verification (<N> dispatches, <M> parcels, <STATUS>)
    ```

#### Step 2 (legacy mode)

Legacy-mode is the path for parent projects that don't use the parcel
mechanism. The working sessions wrote entries to 3/4/5 during the run;
wind-down appends those entries to parent governance files. This path
is retained for non-LogRings consumers.

For EACH of the three run-file → parent-file pairs from Step 1b (skipping
any pair where the parent file does not exist):

2a-legacy. Read the run file at `__RUN_DIR__/<run-file>` (3-TODO.md,
    4-DECISIONS.md, or 5-CHANGELOG.md).

2b-legacy. Read the existing parent file. Identify any potential semantic
    conflicts between the new entries (in the run file) and existing
    entries (in the parent file). A conflict is: same key/topic with
    contradictory status, a decision reversal, a TODO that supersedes an
    earlier TODO, etc. Same key/topic with NON-contradictory new info
    (e.g. additional commentary on the same decision) is NOT a conflict.

2c-legacy. Append the run file's new entries (NOT the heading; just the
    entries) to the bottom of the parent file. Existing parent content
    MUST be preserved verbatim — do NOT modify, reorder, or remove any
    existing line. If the parent file documents an "insertion point"
    (e.g. a comment like `<!-- new entries below -->`), insert there
    instead of appending to the bottom.

2d-legacy. Run `git add <parent-file> && git commit` with the EXACT
    message:

    ```
    wind-down: ingest <run-file> → <parent-file>
    ```

    Where `<run-file>` is the basename (e.g. `3-TODO.md`) and
    `<parent-file>` is the relative path from the worktree root (e.g.
    `TODO.md` or `docs/decisions/DECISIONS.md`). The commit message uses
    a literal Unicode arrow `→` (U+2192).

2e-legacy. After all three potential ingestions, append a "Potential
    governance conflicts" subsection to the `## Wind-down` block of
    `__RUN_DIR__/7-SUMMARY.md`. For each conflict found in 2b-legacy,
    use this EXACT schema:

    ```markdown
    ### Potential governance conflicts

    #### Conflict 1
    - **Source:** `<run-file>:<entry-id-or-line>` — `<one-line summary of new entry>`
    - **Target:** `<parent-file>:<entry-id-or-line>` — `<one-line summary of existing entry>`
    - **Reading:** <1-3 sentences explaining the conflict>
    - **Recommended resolution:** <supersede / merge / clarify / no action>
    ```

    If no conflicts were detected, the subsection MUST contain exactly the
    literal line:

    ```
    _No potential conflicts detected._
    ```

    so absence of the section is distinguishable from absence of conflicts.

   Note: `2-OBJECTIVE.md` and `7-SUMMARY.md` are NOT ingested into the
   parent project. They remain in the archived run folder for human review.
   Do NOT attempt to commit them outside the run folder.

## MUST NOT

- Do NOT delete or rewrite ANY existing parent governance content. Append-only.
- Do NOT create parent governance files where none exist. (Legacy-mode only:
  if 3-TODO.md has content but the parent has no TODO file, SKIP ingestion and
  record the skip in 7-SUMMARY.md.)
- **Do NOT retroactively create parcels in parcel-mode.** The working sessions
  own parcel authoring. Wind-down only surfaces gaps in 7-SUMMARY.md.
- Do NOT touch any file outside (a) parent governance files (legacy-mode only)
  and (b) the run folder __RUN_DIR__. Working files (file-a.txt, src/foo.py,
  etc.) are already committed by the working session(s) — leave them alone.
- Do NOT attempt to merge to a base branch. There is no base branch in
  run-in-place; orchestra commits directly on HEAD throughout the run.
- Do NOT push to any remote. The operator handles the feature → main rollup
  manually after wind-down.

## Failure handling

### Ingestion ambiguity (Step 1 / 2)

If you cannot determine where to ingest a given run-file (parent shape
ambiguous, multiple equally-likely candidates, etc.):

1. Log the skip in 7-SUMMARY.md's `## Wind-down → ### Governance mapping`
   block (e.g. "3-TODO.md → (skipped — ambiguous: TODO.md and docs/TODO.md
   both exist)").
2. Proceed with the next file. Skipped ingestion is preferable to wrong
   ingestion.

### Step 2 verification commit fails (rare)

If `git commit` of the 7-SUMMARY.md update fails (pre-commit hook
regression, disk full, etc.):

1. Write `__RUN_DIR__/6-HANDOVER.md` with the wind-down BLOCKED shape:

   ```
   # Wind-down BLOCKED: Step 2 verification commit failed

   ## Commit error
   <output of the failed git commit>

   ## Manual resolution
   1. Resolve the underlying issue (fix the hook, free disk, etc.).
   2. cd to the worktree.
   3. git add __RUN_DIR__/7-SUMMARY.md && git commit -m "wind-down: governance verification (manual)"
   4. The orchestra archive step is then up to the operator.
   ```

2. Emit `BLOCKED` as the LAST line of your output (on its own line).
   The orchestrator will write a WIND-DOWN-FAILED marker and surface
   recovery instructions to the user.

## Exit signal

On successful wind-down (verification done, 7-SUMMARY.md committed, ready
for the orchestrator to archive the run folder): print exactly `COMPLETE`
as the LAST line of your output, on its own line.

On unresolvable verification-commit failure: print exactly `BLOCKED` as
the LAST line of your output, on its own line.
